1 · RStudio and the workbench

R and RStudio are not the same

R

  • The statistical programming language
  • Performs calculations
  • Stores objects in a running R session
  • Can run without RStudio

RStudio

  • An integrated development environment, or IDE
  • Provides an editor, Console, plots, Help, projects, and Git tools
  • Sends instructions to R
  • Does not replace R

If RStudio opens but R is not installed or configured, the interface exists but there is no R engine available to execute your code.

The four primary panes

Pane What it contains Use it for
Source Saved .R, .Rmd, and .qmd files Writing work that should persist
Console The current interactive R session Short experiments and immediate feedback
Environment Objects currently held in memory; History and Git tabs Inspecting temporary session state
Output Files, Plots, Packages, Help, Viewer Inspecting files, results, and documentation

Pane locations can be customized. Learn their functions, not merely their default positions.

The Console is a conversation with the current session

2 + 2

x <- c(4, 7, 9)
mean(x)

Useful for

  • Testing one expression
  • Asking for help: ?mean
  • Inspecting an object: str(x)

Not a durable record

  • Commands may be incomplete or out of order
  • Objects disappear when the session ends
  • Console history does not explain analytical decisions

Your first saved .R script

File → New File → R Script, then save as analysis.R.

# Summarize the synthetic clinic data
clinic <- read.csv("data/clinic_summary.csv")

n_records <- nrow(clinic)
mean_age <- mean(clinic$age, na.rm = TRUE)

n_records
mean_age

An .R file contains R instructions and comments. It does not automatically contain formatted narrative or the results produced when the code runs.

Run a line, a selection, or the entire script

Action RStudio command Appropriate use
Current line or selection Ctrl-EnterCtrl-Enter / Cmd-EnterCmd-Enter Develop and inspect small steps
Entire script Source button or source("analysis.R") Test whether the saved script is complete
Restart R Ctrl-Shift-F10Ctrl-Shift-F10 / Cmd-Shift-0Cmd-Shift-0 Remove hidden session state

Running selected lines answers “does this step work now?” Sourcing after a restart answers “does the saved script contain everything it needs?”

Console versus .R script

Console .R script
Immediate feedback Yes Yes, when sent to R
Saved deliberately No Yes
Easy to rerun in order Fragile Yes
Contains formatted report text No No
Best role Exploration Reusable analysis instructions

2 · R Markdown documents

R Markdown is the practical starting point

You will meet .Rmd constantly—in existing analyses, package vignettes, collaborators’ reports, and online examples. It remains a supported and widely used format for R-based reporting.

An R Markdown document combines narrative, executable R code, and computed results in one inspectable source file.

Anatomy of an .Rmd

---
title: "Baseline summary"
output: html_document
---

The report contains **prose** and computed results.


::: {.cell}
::: {.cell-output .cell-output-stdout}

```
[1] 50.58333
```


:::
:::

Three layers: YAML says what to create; Markdown explains the analysis; an R chunk performs the computation. rmarkdown, knitr, and Pandoc turn the source into the report.

What .Rmd adds to an .R script

.R script .Rmd document
R code and comments Explanatory Markdown plus executable R chunks
Results appear in Console or plot device Results are placed into a rendered report
Usually one stream of commands Organized into named analytical sections
Excellent for reusable functions and pipelines Excellent for an analysis narrative and report

These formats complement one another. A report may source() functions from an .R file while keeping the statistical explanation in .Rmd.

R Markdown YAML: what should be produced?

---
title: "Synthetic clinic summary"
author: "Student name"
date: "2026-08-25"
output:
  html_document:
    toc: true
---
  • YAML is between the opening and closing --- lines.
  • R Markdown uses the output: key.
  • Indentation expresses nesting; spaces after colons matter.
  • Start with HTML because it requires no LaTeX installation.

Markdown supplies the narrative structure

# Main heading

## Data check

The analysis uses **synthetic data**.

- first item
- second item

[R documentation](https://www.r-project.org/)

Markdown is plain text. It remains readable even before the document is knitted.

r Execute the chunk with R

Three options students commonly confuse

R Markdown option Does the code run? Is code shown? Are results shown?
default Yes Yes Yes
echo=FALSE Yes No Yes
eval=FALSE No Yes No
include=FALSE Yes No No

include=FALSE is ideal for a setup chunk: packages and data are loaded, but the setup code and all its output are omitted from the report.

Useful R Markdown chunk options

Option Example Effect
Show source echo=FALSE Hide code but retain its results
Execute eval=FALSE Display code without running it
Include anything include=FALSE Run but omit code, results, plots, messages, and warnings
Text output results='hide' Run but hide printed text output
Messages message=FALSE Hide package and function messages
Warnings warning=FALSE Hide warnings after you have investigated them
Figure size fig.width=7, fig.height=4 Set figure dimensions in inches
Figure caption fig.cap='Marker by group.' Add a caption to the generated figure

Never suppress a warning merely to make the report look clean. Read it, understand it, and then decide whether suppression is appropriate.

A setup chunk establishes document-wide defaults

Individual chunks can override these defaults in their own headers.

Inline R keeps numbers connected to calculations

Write this in the R Markdown prose:

The dataset contains `r nrow(clinic)` records, with a mean
age of `r round(mean(clinic$age), 1)` years.

It renders as a sentence containing the current calculated values.

If a number comes from the data, calculate it in code or inline R. Do not type a copy of the result into the narrative.

Knit means process the complete document

In RStudio, use the Knit button or run:

rmarkdown::render("report.Rmd")
  1. Read the YAML.
  2. Execute R chunks in document order.
  3. Insert code, results, figures, and inline values as requested.
  4. Use Pandoc to produce the selected output format.
  5. Write a generated .html, .docx, or .pdf file.

3 · Quarto

Apply the same document model in .qmd

These ideas do not change:

  • Markdown provides headings, prose, lists, and links.
  • Fenced {r} chunks contain ordinary R code.
  • knitr executes R chunks from top to bottom.
  • Inline R inserts calculated values into prose.
  • Source remains separate from generated output.
  • A complete render should not depend on objects left in the Environment pane.

Quarto changes selected authoring and publishing syntax; it does not change the R language or the logic of the analysis.

The Quarto-specific changes for today

Feature In the .Rmd block In a .qmd
File extension .Rmd .qmd
Output key output: html_document format: html
Button in RStudio Knit Render
Local option style {r fig1, echo=FALSE} #\| label: fig1 and #\| echo: false
Figure dimensions fig.width=7 fig-width: 7
Document defaults knitr::opts_chunk$set() execute: in YAML, or knitr defaults

The course will normally use Quarto for new reports, while expecting students to read and maintain R Markdown correctly.

What Quarto does

Two things follow from this picture, and both matter:

  • knitr executes the document in order during rendering. Anything the report needs must be created or loaded by saved source.
  • The source is one file; the outputs are many. You never maintain an HTML and a Word version by hand.

Anatomy of a .qmd

Three kinds of content, and nothing else:

---                                    ← 1. YAML header: how to render
title: "Blood pressure at 12 weeks"
format: html
---

## Baseline characteristics            ← 2. Prose: markdown

Mean baseline SBP was 149.9 mmHg.

```{r}                               ← 3. Code chunk: executed
#| label: fig-sbp
#| fig-cap: "SBP by arm at 12 weeks."
boxplot(sbp_12 ~ arm, data = trial)
```

The YAML header is the only part with strict syntax. Indentation and the space after each colon both matter.

The YAML header

---
title: "Blood pressure at 12 weeks"
author: "Shilin Zhao"
date: today
format:
  html:
    toc: true
    code-fold: true
    embed-resources: true
execute:
  echo: false
  warning: false
---
Key Does
format: The output type, and its options. output: in R Markdown
toc: true Table of contents
code-fold: true Code hidden behind a toggle — useful for a clinical audience
embed-resources: true One self-contained HTML file you can email
execute: Document-wide chunk defaults

Code chunks

```{r}
#| label: fig-sbp-arm
#| fig-cap: "Systolic BP at 12 weeks by treatment arm."
#| fig-width: 7
#| fig-height: 3.5
#| echo: true

boxplot(
  sbp_12 ~ arm,
  data = trial,
  xlab = "Treatment arm",
  ylab = "SBP at 12 weeks (mmHg)"
)
```
  • Options go inside the chunk, on #| lines, at the top. Not in the header.
  • One option per line, key: value, YAML syntax.
  • label is optional but makes error messages and cross-references usable.

This is the biggest visible change from R Markdown, where options lived in the chunk header: ```{r fig-sbp, echo=TRUE}.

The chunk options that matter

Option Effect Use when
echo: false Hide the code, show the output Writing for a non-technical reader
eval: false Show the code, don’t run it Teaching, or documenting a slow step
include: false Run it, show nothing Setup chunks — library() calls, data loading
warning: false
message: false		 Suppress those streams Tidy output — after you have read them once
error: true Keep rendering despite an error Deliberately demonstrating a failure
fig-width, fig-height Figure size in inches Always, for anything published
cache: true Reuse results unless the chunk changes An expensive step

warning: false is for a finished document. Suppressing warnings you have never read is how you ship a bug.

Inline code

Write this in your prose:

Mean baseline SBP was `r round(mean(trial$sbp_0), 1)` mmHg
in `r nrow(trial)` patients.

And it renders as:

Mean baseline SBP was 149.9 mmHg in 60 patients.

Important

This is the feature that removes an entire class of error. A number typed into prose by hand becomes wrong the moment the data changes — and nothing will tell you. A number computed inline cannot.

Figures come from code

boxplot(
  sbp_12 ~ arm,
  data = trial,
  xlab = "Treatment arm",
  ylab = "SBP at 12 weeks (mmHg)",
  col = c("grey85", "grey55")
)

Figure 1: Systolic BP at 12 weeks by treatment arm.

Cross-reference it in prose as @fig-sbp-live and Quarto numbers it for you.

4 · Why reproducibility matters

A case worth knowing

Duke University, 2006–2011. Papers claimed that gene-expression signatures could predict which chemotherapy a patient would respond to. Three clinical trials enrolled patients on the strength of the work.

When Keith Baggerly and Kevin Coombes tried to reproduce the analyses, they reported problems including shifted gene indices, reversed sensitive/resistant labels, and analyses that could not be reconstructed from the stated methods.

The trials were suspended and stopped; multiple papers were retracted. The case contributed to a major review of how omics-based tests enter clinical use.

Detailed analysis: Baggerly & Coombes (2009). Timeline and policy review: Institute of Medicine (2012).

Three words that get confused

Term Means Needs
Reproducible Same data, same code → same result Organized source and documented inputs
Replicable New data, same question → same conclusion A new study
Generalizable The conclusion holds beyond the sample Theory and external validity

Only the first is directly under the analyst’s control, and it is the minimum needed for someone else to evaluate the computation.

The two ways analyses fail

It will not run

Missing files, unavailable data mounts, uninstalled packages, or undocumented manual steps.

Annoying, but visible.

It runs and is wrong

Wrong file silently read, stale object left in memory, or a result edited by hand.

Dangerous, because it looks finished.

A saved script and a document rendered from its source make the second class of failure easier to detect.

5 · Reproducible project workflow

Projects give the analysis a stable home

Open the supplied .Rproj file, or use File → New Project → Existing Directory.

bios6301-session01/
├── bios6301-session01.Rproj
├── analysis.R
├── report.Rmd
├── report.qmd
└── data/
    └── clinic_summary.csv
  • Opening the project establishes a predictable project root.
  • Relative paths are interpreted from that project context.
  • The project folder becomes a natural Git repository in Session 2.
  • Source files and input data remain distinct from generated output.

Paths are a design choice

Data inside the project

clinic <- read.csv(
  "data/clinic_summary.csv"
)

Relative paths are convenient for course-sized, shareable data.

Large or protected data elsewhere

data_root <- "D:/shared/study123"
clinic <- readRDS(file.path(
  data_root, "derived/cohort.rds"
))

An absolute root is often correct on a server, cluster, or shared drive.

setwd() is legitimate when the working directory is chosen deliberately. For collaboration, define a machine-specific location once and document the required drive, mount, or environment.

Restarting R tests saved source

rm(list = ls())

This removes objects, but loaded packages, changed options, working-directory changes, and other process state can remain.

Tip

Use Session → Restart R for a genuinely fresh process, then source the .R script or render the complete document from the project.

The standing rule of this course

Every submission must render from a clean session in its documented computing environment.

Before you submit, every time:

  1. Restart R — Ctrl-Shift-F10Ctrl-Shift-F10
  2. Render the whole document from scratch
  3. Confirm the output is what you expect — not just that it succeeded
  4. Confirm every external data location is defined once and documented
  5. Confirm there is no install.packages() or hidden manual step in the report

Rendering already uses a fresh session, so a document that renders is close to verified. Restarting first catches the remaining case: a file that quietly depends on something you did in the console.

Summary

  • Reproducibility is a statistical concern, not end-of-project clerical work.
  • R Markdown and Quarto both keep prose, code, and computed results together.
  • Use relative paths for project data; use documented absolute roots for large or protected data stored elsewhere.
  • This course begins from .Rmd literacy and focuses new work on .qmd.
  • Inline values and generated tables prevent copy-and-paste drift.
  • A clean-session render tests whether the source is complete.
