1 · Conditions

A calculation can run and still be wrong

A script receives four baseline readings but only two follow-up readings. It should flag the mismatch before calculating paired changes.

baseline <- c(150, 140, 160, 155)
followup <- c(138, 132)
followup - baseline
[1] -12  -8 -22 -23
Situation What the script should do
Different numbers of readings Flag the mismatch and skip the calculation
Equal numbers of already matched readings Calculate follow-up minus baseline

R reused the two follow-up values and returned four changes without a warning. We need one decision about whether the calculation should run at all.

What if does

if chooses which block of code runs. Its condition must give one nonmissing logical value: TRUE or FALSE.

if (condition) {
  # Run this block when the condition is TRUE.
} else {
  # Run this block when the condition is FALSE.
}

Use it when the next action depends on the current inputs: calculate paired changes or report an input problem. Only the chosen branch runs.

Check the inputs before calculating

if (length(followup) != length(baseline)) {
  "Check the input: baseline and follow-up counts differ"
} else {
  followup - baseline
}
[1] "Check the input: baseline and follow-up counts differ"

The comparison of lengths gives one TRUE or FALSE. Here it is TRUE, so R returns the message and does not run the subtraction in else.

Equal lengths are necessary; the readings must also belong to the same people in the same order. This check cannot establish that alignment.

More than two cases: else if

n_missing <- sum(is.na(trial_raw$sbp_12))
if (n_missing == 0) {
  "No outcomes are missing"
} else if (n_missing == 1) {
  "One outcome is missing"
} else {
  "Multiple outcomes are missing"
}
[1] "Multiple outcomes are missing"

Conditions are checked in order; the first matching branch runs. The final else handles the remaining case. Keep } else { together and use braces for each block.

A vector is not one decision

if (trial$sbp_0 > 140) "above cutoff" else "at or below cutoff"
Error in if (trial$sbp_0 > 140) "above cutoff" else "at or below cutoff": the condition has length > 1
head(trial$sbp_0 > 140)
[1]  TRUE  TRUE  TRUE  TRUE  TRUE FALSE
length(trial$sbp_0 > 140)
[1] 60

There is one comparison per participant, but if requires one decision. The repair depends on the intended question: one label per participant, or one answer about the whole group? The cutoff is only a coding example.

One label per participant: ifelse()

above <- trial$sbp_0 > 140
labels <- ifelse(above, "above cutoff", "at or below cutoff")
head(data.frame(sbp = trial$sbp_0, above, label = labels))
  sbp above              label
1 160  TRUE       above cutoff
2 162  TRUE       above cutoff
3 157  TRUE       above cutoff
4 157  TRUE       above cutoff
5 146  TRUE       above cutoff

length(labels)
[1] 60

ifelse() makes an elementwise choice: one comparison and one returned label per participant. This is the vectorized conditional introduced in Session 3.

It repairs the preceding code if the goal is a label for every row.

One group decision: any() or all()

c(at_least_one = any(above), every_participant = all(above))
     at_least_one every_participant
             TRUE             FALSE 
if (any(above)) {
  "At least one participant is above the cutoff"
} else {
  "No participant is above the cutoff"
}
[1] "At least one participant is above the cutoff"
if (all(above)) "Everyone is above" else "Not everyone is above"
[1] "Not everyone is above"

any() and all() reduce the vector to one logical value, suitable for if. They answer different group questions; neither produces a label for every row. The measurements in this example are complete.

Match the tool to the question

Intended result Tool
One action based on a single condition if (...) ... else ...
One label for each value ifelse(test, yes, no)
One action if at least one value meets a rule if (any(test)) ...
One action if every value meets a rule if (all(test)) ...

An if expression can also supply a value for assignment:

label <- if (n_missing > 0) "missing outcomes present" else "no missing outcomes"
label
[1] "missing outcomes present"

A missing condition is a separate problem

sbp <- NA_real_
if (sbp > 140) "above cutoff" else "at or below cutoff"
Error in if (sbp > 140) "above cutoff" else "at or below cutoff": missing value where TRUE/FALSE needed

The condition has length one, but its value is unknown. Handle that case explicitly:

if (is.na(sbp)) {
  "measurement missing"
} else if (sbp > 140) {
  "above cutoff"
} else {
  "at or below cutoff"
}
[1] "measurement missing"

NA is not FALSE; missing measurements need a stated reporting rule.

Missing values in a group decision

x <- c(120, NA, 155)
c(observed = sum(!is.na(x)),
  any_observed_above = any(x > 140, na.rm = TRUE),
  all_observed_above = all(x > 140, na.rm = TRUE))
          observed any_observed_above all_observed_above
                 2                  1                  0

na.rm = TRUE changes the question to the observed measurements. It does not show what the missing measurements would have been.

Without removal, a missing comparison can leave any() or all() unresolved. Report the observed count alongside a result that excludes missing values.

An empty condition is a separate problem

sbp <- numeric(0)  # No values remain after filtering; this is not the number 0.
if (sbp > 140) "above cutoff"
Error in if (sbp > 140) "above cutoff": argument is of length zero

Check availability before asking a question that requires observed data:

if (sum(!is.na(sbp)) == 0) {
  "No observed measurements"
} else if (any(sbp > 140, na.rm = TRUE)) {
  "At least one observed measurement is above the cutoff"
} else {
  "No observed measurement is above the cutoff"
}
[1] "No observed measurements"

all(logical(0)) is TRUE and any(logical(0)) is FALSE. Neither establishes that measurements were available.

Scalar and elementwise operators

Need Operators Example
Combine checks for each value &, | !is.na(x) & x > 140
Combine single decisions &&, || length(x) > 0 && all(is.finite(x)) 
candidate <- NA_real_
is.numeric(candidate) && length(candidate) == 1 &&
  !is.na(candidate) && candidate > 0
[1] FALSE

&& stops when the left check is false. Put shape and missingness checks before a comparison that assumes one observed value.

What copy-paste actually costs

Cost What repeated copies make harder
Reading A reader has to diff four blocks to find the one word that differs
Changing If missing values arrive, update the missing-value policy in every copy; overlooking one gives inconsistent summaries
Naming The block has no name, so you cannot say what it does, reuse it, or check it
Divergence If one copy later adds round(..., digits = 2) and the others do not, the reporting rules diverge

The preceding code does not round any results. Rounding is an example of a future change that must be kept consistent across copies.

By the end of today that block is one line:

summarise_by_arm(trial, sbp_0)

A contract before code

For a reusable summary, decide what the caller can rely on.

Part Decision
Input A numeric vector, possibly containing missing values
Options Rounding precision and whether to remove missing values
Output Named values with a documented meaning for n
Edge cases What happens with no observations or the wrong input type?

Quick discussion: should n count all rows or observed measurements? What label would make that choice clear?

Read the parts of a function call

Before writing a function, read the interface of one you already use.

median_result <- stats::median(x = c(120, NA, 140), na.rm = TRUE)

Package namespaces identify which function

A namespace holds a package’s objects and keeps its names separate from those in other packages. package::function selects an exported function.

Explicit name Purpose
stats::median() Compute a median
dplyr::filter() Select rows of a data frame
stats::filter() Filter a time series, for example with a moving average
  • The package must be installed. :: loads its namespace as needed.
  • You do not need to call library() first.
  • An explicit package name avoids confusion when packages share a function name.

Parameters define the interface; arguments fill it

Parameters, or formal arguments, are the names in the definition. The help page’s Usage section shows them and their defaults:

median(x, na.rm = FALSE, ...)
Parameter Meaning Argument in our call
x Data to summarize; no default c(120, NA, 140)
na.rm Remove missing values? Default: FALSE TRUE
... Further arguments for methods; unused by the default method None supplied

The Arguments section explains accepted inputs. Omitting na.rm uses FALSE; supplying na.rm = TRUE overrides that default.

The return value is an object you can use

Our call returned one numeric value, 130. We saved it in median_result. The help page’s Value section describes the result’s type and length.

typeof(median_result)
[1] "double"
length(median_result)
[1] 1
median_result + 10
[1] 140

Returning makes an object available to the caller. Printing displays it. Assignment stores the result without automatically printing it.

Your first function, from your own code

First extract the numeric summary used inside each repeated block. Grouping will return in Section 6; this helper summarizes one numeric vector.

# Return n, mean, and SD of a numeric vector, rounded.
sbp_summary <- function(x, digits = 1) {
  result <- c(n = length(x), mean = mean(x), sd = sd(x))
  return(round(result, digits))
}

Missing data requires an explicit design decision

Suppose the new input is c(120, NA, 140). What should n mean?

Policy Observed count Reported mean Reported SD
Keep missingness in the calculation 2 NA NA
Summarize the observed measurements 2 130 About 14.1

We will define n as the observed count and add na_rm = TRUE as the default. The caller can choose FALSE to preserve missingness in mean and SD.

The count and the missing-data rule are separate decisions. State both.

Arguments and defaults

# n counts non-missing values, so the reported n matches the mean.
sbp_summary <- function(x, digits = 1, na_rm = TRUE) {
  return(round(c(
    n    = sum(!is.na(x)),
    mean = mean(x, na.rm = na_rm),
    sd   = sd(x, na.rm = na_rm)
  ), digits))
}

Use or override a default

sbp_summary(trial_raw$sbp_12)
    n  mean    sd
 57.0 141.3  15.3 
sbp_summary(trial_raw$sbp_12, na_rm = FALSE)
   n mean   sd
  57   NA   NA

A default is what the argument is when the caller says nothing. Choose the safe, common case — then let the caller override it.

How R matches arguments

Three ways, tried in this order: exact name, then partial name, then position.

sbp_summary(trial$sbp_0, 2)                 # position
     n   mean     sd
 60.00 149.47  11.85 
sbp_summary(digits = 2, x = trial$sbp_0)    # exact name — order stops mattering
     n   mean     sd

Partial matching works, and is a trap:

report <- function(x, na_rm = FALSE, names = TRUE) return("ok")
report(1, n = TRUE)
Error in report(1, n = TRUE): argument 2 matches multiple formal arguments

House rule: data argument by position, everything else by full name. Partial names break the day somebody adds an argument.

Make the return explicit

Use return(value) at every normal exit, including the end of the function.

mean_sbp <- function(x) {
  return(mean(x))
}
quiet_mean <- function(x) {
  return(invisible(mean(x)))
}
mean_sbp(c(120, 140))         # automatically prints 130
[1] 130
quiet_mean(c(120, 140))       # no automatic printing
print(quiet_mean(c(120, 140))) # explicitly prints 130
[1] 130

return() ends the call. invisible() suppresses automatic printing; the returned value is still available to the caller.

Choose a return shape for the next step

Return shape Useful when Caller extracts a result with
One number The next step needs only one statistic Use the result directly
Named numeric vector Several results share a numeric type answer["mean"]
Named list Results need different types or structures answer$mean

Our sbp_summary() returns a named numeric vector. A future report might also need a text status or a table; that would justify a list.

Choose and document the shape before writing downstream code. Changing it later can break callers even if the numbers are unchanged.

c(mean = 130, status = "ok") makes both entries character. A list can retain the numeric mean and a character status separately.

Return several results in one list

A function returns one object. That object can be a list containing several named results. Here we want the observed count, missing count, and observed mean.

describe_measurements <- function(x) {
  return(list(n_observed = sum(!is.na(x)),
       n_missing = sum(is.na(x)),
       mean = mean(x, na.rm = TRUE)))
}

return(list(...)) returns the whole list as one object. It does not return only the last component, mean.

4 · Scope

Where R looks for a name

Step 2 is where the function was written, not where it was called from. That is what “lexical” means.

The global that vanishes

threshold <- 140

is_high <- function(sbp) return(sbp > threshold)   # threshold is not an argument

sum(is_high(trial$sbp_0))
[1] 50

It works. Now restart R — or hand the script to a colleague:

rm(threshold)
sum(is_high(trial$sbp_0))
Error in is_high(trial$sbp_0): object 'threshold' not found

This is the honest failure. It is annoying, and it tells you immediately.

A hidden input changes the answer

This version reads threshold from outside the function. It looks up that variable each time it is called; it does not keep its original value.

threshold <- 140
is_high <- function(sbp) return(sbp > threshold)
sum(is_high(trial$sbp_0))
[1] 50

A sensitivity analysis changes the external variable. The same call now uses that new value:

threshold <- 160        # for the sensitivity analysis
sum(is_high(trial$sbp_0))
[1] 8

The data and function definition are unchanged. The answer changes because threshold is a hidden input: the first call uses 140 and the second uses 160.

Everything comes in through an argument

# Flag patients above a systolic threshold. Threshold is an argument so the
# result depends only on what the caller passed.
is_high <- function(sbp, threshold = 140) {
  return(sbp > threshold)
}

sum(is_high(trial$sbp_0))
[1] 50
sum(is_high(trial$sbp_0, threshold = 160))
[1] 8

The rule: a function’s return value should depend only on its arguments. Nothing else.

The sensitivity analysis is now a second call, visible on the page, instead of a reassignment fifty lines away.

5 · Validation

Fail loudly, or be wrong quietly

mean_weight <- function(weight_kg) return(mean(weight_kg))

mean_weight(trial_raw$weight_kg)   # one weight is recorded as -99
[1] 80.275
mean_weight(trial$weight_kg)       # the same cohort, repaired
[1] 83.22

80.3 kg against 83.2 kg. Both are plausible. Only one is right, and the function had no opinion about which.

Important

A function that fails loudly on bad input is safer than one that returns a plausible wrong answer.

stopifnot()

checked_mean <- function(x, digits = 1) {
  stopifnot(is.numeric(x), length(x) > 0, digits >= 0)

  return(round(mean(x, na.rm = TRUE), digits))
}

checked_mean(trial$arm)
Error in checked_mean(trial$arm): is.numeric(x) is not TRUE

Give failed checks a useful message

Name the checks and you choose the message:

checked_mean <- function(x, digits = 1) {
  stopifnot(
    "x must be a numeric vector" = is.numeric(x),
    "digits must not be negative" = digits >= 0
  )
  return(round(mean(x, na.rm = TRUE), digits))
}

checked_mean(trial$arm)
Error in checked_mean(trial$arm): x must be a numeric vector

stop() and guard clauses

# Mean weight, refusing sentinel codes. Site 3 used -99 for "not recorded",
# and averaging those understates the mean by about 3 kg.
mean_weight <- function(weight_kg) {
  if (any(weight_kg < 20, na.rm = TRUE)) {
    stop("weight_kg contains values below 20: check for sentinel codes",
         call. = FALSE)
  }
  return(mean(weight_kg, na.rm = TRUE))
}

mean_weight(trial_raw$weight_kg)
Error: weight_kg contains values below 20: check for sentinel codes

A guard clause is a check at the top that exits early. It keeps the happy path unindented and the failure cases visible.

How much validation is enough

Check Because
Type and shape is.numeric(), is.data.frame(), length(), column names present
Values that cannot be real Negative weights, ages over 120, proportions above 1
What your code silently assumes Sorted rows, one row per patient, non-empty groups

mean("a") warns and returns NA; it does not stop. Validate numeric input when a missing result would hide a data-type error.

Rule of thumb: validate what a collaborator’s file could plausibly get wrong. Two or three checks is usually right.

Specify the edge cases

Our safe_mean() contract accepts numeric vectors with finite values or NA/NaN. It returns one numeric value and ignores missing observations.

Input Required behavior
c(2, 4, NA) Return 3
numeric(0) Return NA_real_
c(NA_real_, NA_real_) Return NA_real_
"4", a matrix, or a data frame Stop with a useful message
c(2, Inf) Stop because infinity is outside this contract

NA_real_ explicitly creates numeric missingness. c(NA, NA) is logical, so use typed missing values when constructing a numeric teaching column.

Build safe_mean() with guard clauses

safe_mean <- function(x) {
  if (!is.numeric(x) || !is.null(dim(x))) {
    stop("x must be a numeric vector", call. = FALSE)
  }
  if (any(is.infinite(x))) {
    stop("x must not contain infinite values", call. = FALSE)
  }
  if (all(is.na(x))) return(NA_real_)
  return(mean(x, na.rm = TRUE))
}
safe_mean(c(2, 4, NA))
[1] 3
safe_mean(numeric(0))
[1] NA

The empty case also exits because all(logical(0)) is TRUE.

Trace the branch that ends the call

Follow safe_mean() from top to bottom. Stop tracing when a guard exits.

Input First exit Result Does mean() run?
"4" Type guard: stop() Error No
c(2, Inf) Infinite-value guard: stop() Error No
c(NA_real_, NA_real_) return(NA_real_) One numeric NA No
c(2, NA, 4) Last expression 3 Yes

For numeric(0), the first two guards pass and all(is.na(x)) is TRUE. The early return supplies one numeric NA, not an empty vector.

Explain why the shorter version changes the contract

mean_shortcut <- function(x) return(mean(x, na.rm = TRUE))
mean_shortcut(numeric(0))
[1] NaN
safe_mean(numeric(0))
[1] NA

Both run. The first returns NaN; our helper returns NA_real_ by design.

Ask which behavior a report expects, and document it. A shorter implementation is useful only if it preserves the intended input and output rules.

centre_values <- function(x, centre = 0) {
  stopifnot(
    "x must be a numeric vector" = is.numeric(x) && is.null(dim(x)),
    "centre must be one finite number" =
      is.numeric(centre) && length(centre) == 1 &&
      is.null(dim(centre)) && is.finite(centre)
  )
  return(x - centre)
}

Validate the type, then the length, then the value. An expected failure is also evidence that the interface works; try centre_values(1:3, centre = NA).

Interpret the comparison

identical() checks exact equality. all.equal() returns TRUE or a description of differences. Use isTRUE(all.equal(old, new)) for a logical check.

Compose two functions for paired measurements

classify_change <- function(change) {
  stopifnot(is.numeric(change), is.null(dim(change)))
  out <- rep("missing", length(change))
  observed <- !is.na(change)
  out[observed & change < 0] <- "decrease"
  out[observed & change >= 0] <- "no decrease"
  return(out)
}
classify_change(c(-2, 1, NA, 0))
[1] "decrease"    "no decrease" "missing"     "no decrease"

This returns a character vector even for zero rows. It describes the sign of change, not whether a change is clinically meaningful.

A reusable paired-change calculation

change_summary <- function(baseline, followup) {
  stopifnot(is.numeric(baseline), is.null(dim(baseline)),
            is.numeric(followup), is.null(dim(followup)),
            length(baseline) == length(followup),
            !any(is.infinite(baseline)), !any(is.infinite(followup)))
  change <- followup - baseline
  return(data.frame(change = change, category = classify_change(change)))
}
change_summary(c(10, 8, NA, 12), c(8, 9, 7, 12))
  change    category
1     -2    decrease
2      1 no decrease
3     NA     missing
4      0 no decrease

Precondition: the two vectors refer to the same people in the same order. Equal lengths do not establish patient alignment; join by ID first when needed.

Save a helper separately from the analysis

Keep reusable definitions in an .R file and analysis calls in your report:

The supplied R/centre-values.R contains the validated centre_values(). It defines the function; it does not load data or run an analysis.

Editing the file does not update a function already in memory. Save it, then source it again or render the report again.

Load the saved definition, then call it

In the saved report, with paths relative to its folder:

source("R/centre-values.R")

# [1] -2 NA  2

In the Console, use the path from your personal project root:

source(here::here("work", "session11", "R", "centre-values.R"))

source() executes the file’s R expressions. The function definition binds its name; the later call supplies data and returns centered values.

Reuse should survive a fresh session

  1. Copy the supplied R folder beside your report.
  2. Put your other completed helpers in R/functions.R.
  3. Add both source() calls to the report before the first function call.
  4. Remove duplicate definitions from the report after checking equivalence.
  5. Restart R and render the report using its saved source.

If a function is missing, inspect the source path and execution order. If an old result persists, check which file or later definition replaced it.

Evidence: the fresh render reproduces the expected values and checks without manually running definitions in the Console first.

House style for functions

Rule In practice
Verbs for functions, nouns for objects summarise_by_arm(), not arm_summary()
snake_case, no exceptions plot_by_arm, not plotByArm
One job per function If the name needs “and”, it is two functions
Make exits explicit Use return(value) at every normal exit
Keep it focused A long function is a reason to review its responsibilities
Data argument first So it pipes
Validate inputs Two or three checks, at the top
One line above saying what it does What it takes, what it returns
Comments say why The code already says what
