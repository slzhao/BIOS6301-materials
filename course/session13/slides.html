1 · Doing the same thing many times

Repeat a function whose contract is already checked

Session 11 defined reusable operations; Session 12 checked their behavior. Now repeat an operation over several inputs:

summarise_by_arm(trial, sbp_0)
summarise_by_arm(trial, sbp_6)
summarise_by_arm(trial, sbp_12)
summarise_by_arm(trial, weight_kg)
summarise_by_arm(trial, age)
# ... and eight more outcomes in the final project

The duplication did not disappear. It moved up one level — from the body of the block to the list of calls.

A function names what you are doing. Iteration names what you are doing it to.

Ways to express repeated work

Looks like Gives you
Loop for (v in outcomes) { ... } Nothing. You manage the result yourself
Apply family lapply(outcomes, f) A list, one element per input
purrr map(outcomes, f) A list; typed variants require scalar results
Vectorized sqrt(x), x > 140 The answer, with no iteration written at all

The first three are the same idea with different bookkeeping. The fourth is a direct expression of vector work. Prefer it when its behavior matches the task.

2 · for, while, and pre-allocation

Anatomy of a for loop

for (v in outcomes) {
  cat(v, ":", round(mean(trial[[v]]), 1), "mmHg\n")
}
sbp_0 : 149.5 mmHg
sbp_6 : 144 mmHg
sbp_12 : 141.6 mmHg
  • v takes each element of outcomes in turn. It is a real variable and it survives the loop.
  • trial[[v]] — double brackets, because v holds a name, not a column.
  • This loop prints. It does not produce an object. That is the next slide, and it is where the trouble is.

Store the results of a checked function

marker_means <- setNames(numeric(ncol(markers)), names(markers))
for (j in seq_along(markers)) {
  marker_means[j] <- safe_mean(markers[[j]])
}
marker_means
marker_a marker_b marker_c
     5.1     10.5       NA

safe_mean() is the helper from Sessions 11–12. It handles missingness and validates each column. The loop chooses inputs and stores outputs.

Practice: explain [[j]] versus [j], then predict the result for a data frame with zero columns.

Pre-allocate, do not grow

Same answer, two ways. Watch the clock.

grow <- function(k) {
  out <- numeric(0)                                  # grows on every iteration
  for (i in seq_len(k)) out <- c(out, sqrt(i))
  out
}

prealloc <- function(k) {
  out <- numeric(k)                           # the right size, once
  for (i in seq_len(k)) out[i] <- sqrt(i)
  out
}

Check equality before comparing elapsed time

stopifnot(identical(grow(20000), prealloc(20000)))
system.time(grow(20000))["elapsed"]
elapsed
   4.84 
system.time(prealloc(20000))["elapsed"]
elapsed
      0

Why growing is quadratic

out <- c(out, x) does not append. It allocates a new vector and copies the old one into it, every single iteration.

k seconds
5000 0.35
10000 0.97
20000 3.28

The copying work grows quadratically. Elapsed times also reflect allocation, garbage collection, and measurement noise. Building a vector of length k this way copies about k²/2 values.

rbind()-ing rows onto a data frame inside a loop is the same bug, and worse — a data frame copy is far more expensive than a vector copy.

while: repeat while a condition is true

while (condition) {
  # do one step
  # update the values used by condition
}
  1. Check condition before the first step.
  2. If TRUE, run the body and check the condition again.
  3. If FALSE, skip the body and continue after the loop.

The condition must be one nonmissing logical value. The body may run zero times. Update the state so the condition can become false; otherwise the loop may never end.

Use for to visit a supplied sequence. Use while when a condition determines whether another step is needed.

A bounded while loop, one step at a time

Goal: start at 1 and halve the value until it is below 0.01.

x <- 1
iteration <- 0L
max_iterations <- 100L
while (x >= 0.01 && iteration < max_iterations) {
  x <- x / 2
  iteration <- iteration + 1L
}
c(value = x, iterations = iteration)
     value iterations
 0.0078125  7.0000000

The values are 1 → 0.5 → 0.25 → ... → 0.0078125: seven updates. && requires both conditions to be true. The limit prevents endless iteration if the target is not reached.

Check why the loop stopped

reason <- if (x < 0.01) "threshold reached" else "iteration limit"
reason
[1] "threshold reached"

Stopping is not proof of success: the iteration limit may have ended the loop.

Predict, then rerun from the initialization:

  • Change max_iterations to 3L: what value and stopping reason do you get?
  • Start at x <- 0.005: how many times does the body run?
  • Remove x <- x / 2: does the safeguard still stop the loop?

The next value depends on the previous value; this is a natural use of a loop.

3 · What “vectorized” actually means

The loop is still there. It is in C

A vectorized interface accepts a whole vector. Common primitives such as sum() perform their internal loop in compiled code; not every vector-shaped interface does.

Compare three implementations on the same input

y  <- rnorm(5e5)
tt <- \(expr) system.time(expr)[["elapsed"]]      # seconds, unnamed

c(`for loop`   = tt({
                   out <- numeric(length(y))
                   for (i in seq_along(y)) out[i] <- y[i]^2
                 }),
  `vapply()`   = tt(vapply(y, \(v) v^2, numeric(1))),
  `vectorized` = tt(y^2))
  for loop   vapply() vectorized
      0.05       1.21       0.00

These are local measurements, not universal speed rankings. A functional still calls an R function per element. Check results, repeat timings, and report input size.

The vectorized answers you already have

Instead of looping to… Write
build a new column from an old one trial$high <- trial$sbp_0 > 140
choose per row ifelse(), if_else(), case_when()
total or average a column sum(), mean(), cumsum()
average across visits, per patient rowMeans(), rowSums()
average one visit, across patients colMeans(), colSums()
element-wise max of two vectors pmax(), pmin()
count each value table()
test membership x %in% y
find where a condition holds which()
running total cumsum(), cumprod(), cummax()

Before writing a loop, check whether a function already expresses the operation and has the missing-value behavior you need.

vapply(): declare the shape

FUN.VALUE is a template. It says what one answer looks like.

vapply(trial[outcomes], summary_of, numeric(3))
     sbp_0 sbp_6 sbp_12
n     60.0  60.0   60.0
mean 149.5 144.0  141.6
sd    11.9  15.1   15.1
vapply(split(trial_jun$sex, trial_jun$site), unique, character(2))
Error in vapply(split(trial_jun$sex, trial_jun$site), unique, character(2)): values must be length 2,
 but FUN(X[[3]]) result is length 1

The error names the element that broke the contract: FUN(X[[3]]). That is site 3.

Match the output template to the operation

template <- c(n = 0, mean = 0, sd = 0)
summary_matrix <- vapply(markers, one_summary, template)
summary_matrix
      marker_a  marker_b marker_c
n    3.0000000  4.000000        0
mean 5.1000000 10.500000       NA
sd   0.9539392  1.290994       NA

One statistic per marker: use numeric(1) or map_dbl(). Three statistics per marker: use a length-three template or map().

Practice: predict the dimensions for zero marker columns. Why would vapply(markers, one_summary, numeric(1)) fail?

Input checks and output checks do different jobs

bad <- list(good = c(2, 4), broken = "not numeric")
vapply(bad, safe_mean, numeric(1))
Error: x must be a numeric vector

safe_mean() rejects the invalid input. vapply() checks each output. It does not validate inputs for the function you supply.

mean("not numeric") warns and returns numeric NA. That result can satisfy a numeric output template, even though the input is wrong.

apply(): margins on a matrix

# MARGIN = 1: one answer per ROW
head(apply(sbp_mat, 1, max), 4)

round(apply(sbp_mat, 2, mean), 1)
 sbp_0  sbp_6 sbp_12

apply() on a data frame: the coercion trap

apply(trial[, c("id", "sbp_0", "sbp_12")], 1, max) |> head(4)
[1] "P001" "P002" "P003" "P004"

Those are patient IDs, not blood pressures. apply() needs a matrix, so it called as.matrix() — and a matrix holds one type, so every number became "P001"-style text.

Session 3’s coercion rules, arriving through a new door. apply() on a data frame with any character column silently converts everything to character.

mapply() and Map(): two vectors at once

When you need to walk two things in parallel:

labels <- c("Baseline", "6 weeks", "12 weeks")

mapply(
  \(col, lab) sprintf("%s: %.1f mmHg", lab, mean(trial[[col]])),
  outcomes, labels
)
                 sbp_0                  sbp_6                 sbp_12
"Baseline: 149.5 mmHg"  "6 weeks: 144.0 mmHg" "12 weeks: 141.6 mmHg"

Map() is the same thing without simplification — it is to mapply() what lapply() is to sapply(), and it is the safer default.

5 · Head to head: base and purrr

Base R and purrr list mappings

base R

res <- lapply(trial[outcomes],
              summary_of)
res$sbp_12
    n  mean    sd
 60.0 141.6  15.1

purrr

library(purrr)

res <- map(trial[outcomes],
           summary_of)
res$sbp_12

Both lapply() and map() take data first and return a list. The typed purrr variants make scalar output contracts explicit in the function name.

The base R route is sufficient for the lab. Use the purrr alternatives if the package is installed; compare their results with the base implementation.

Anonymous functions and extra arguments

\(x) is shorthand for function(x). Use it when a small wrapper does not need a separate name.

vapply(trial[outcomes], \(x) round(mean(x), digits = 1), numeric(1))
 sbp_0  sbp_6 sbp_12
 149.5  144.0  141.6 
# The corresponding purrr call
purrr::map_dbl(trial[outcomes], \(x) round(mean(x), digits = 1))

The wrapper receives one column and returns one number. If it returns several statistics, choose a list or a matrix template instead.

map2(), pmap(), and the rest

Job base R purrr
Two vectors in parallel mapply(f, x, y) / Map(f, x, y) map2(x, y, f)
Many vectors in parallel mapply(f, x, y, z) pmap(list(x, y, z), f)
Side effects only — plots, files for / invisible(lapply()) walk(x, f)
Element and its name mapply(f, x, names(x)) imap(x, f)

For map(), data comes first and the function second. map2() takes two inputs before the function. Check each signature; base R also varies by function.

The same job, twice

Task. For every outcome, the treatment-minus-placebo difference in means.

vapply(outcomes, \(v) {
  m <- tapply(trial[[v]],
              trial$arm, mean)
  round(m[["Treatment"]] -
        m[["Placebo"]], 1)
}, numeric(1))
 sbp_0  sbp_6 sbp_12
  -1.5   -9.4  -12.4 
map_dbl(outcomes, \(v) {
  trial |>
    group_by(arm) |>
    summarise(m = mean(.data[[v]])) |>
    pull(m) |>
    diff() |>
    round(1)
}) |> set_names(outcomes)

For this unnamed character input, vapply() uses the strings as output names; map_dbl() preserves existing names, so we set names explicitly here. And v holds a string, so it is .data[[v]] — not last week’s curly-curly, which wants a bare column name.

6 · Choosing, and when a loop is right

Which one do I want?

If… Use
A vectorized function matches the contract Prefer its direct expression of the task
One value per element, type known vapply() / map_dbl()
Results have different shapes lapply() / map()
You are looping for a side effect for loop, or walk()
Step i depends on step i−1 An explicit loop; accumulation tools are another option
You are exploring at the console Whatever is quickest to type

Prefer clear code that satisfies the contract. Measure representative work before deciding that performance justifies a more complex implementation.

A loop with a dependency between steps

Iterative dependence: step i needs the result of step i−1.

# Newton-Raphson. Each step is computed FROM the previous estimate.
x     <- 1
trace <- numeric(4)

for (i in seq_len(4)) {
  x        <- x - (x^2 - 2) / (2 * x)
  trace[i] <- x
}

round(trace, 8)
[1] 1.500000 1.416667 1.414216 1.414214

An independent mapping is not the right model: iteration 3 uses the state created by iteration 2. An explicit loop makes that dependency visible. MCMC, EM, gradient descent, and every iterative optimiser have this shape.

Accumulating results without growing

The pattern for “one row of results per iteration”:

res <- vector("list", length(outcomes))     # pre-allocated LIST
names(res) <- outcomes

for (v in outcomes) {
  res[[v]] <- data.frame(
    outcome = v,
    mean    = round(mean(trial[[v]]), 1),
    sd      = round(sd(trial[[v]]), 1)
  )
}

do.call(rbind, res)                          # combine ONCE, at the end
       outcome  mean   sd
sbp_0    sbp_0 149.5 11.9
sbp_6    sbp_6 144.0 15.1
sbp_12  sbp_12 141.6 15.1

7 · Verify, measure, and practice

Equivalence comes before speed

row_loop <- function(m) {
  out <- numeric(nrow(m))
  for (i in seq_len(nrow(m))) out[i] <- mean(m[i, ])
  names(out) <- rownames(m)
  out
}
stopifnot(isTRUE(all.equal(row_loop(sbp_mat), rowMeans(sbp_mat))))

Check values, missing-value policy, names, types, and dimensions. Two fast implementations of different calculations are not interchangeable.

Measure representative work repeatedly

bench_input <- matrix(seq_len(20000) / 100, nrow = 1000)
stopifnot(isTRUE(all.equal(row_loop(bench_input), rowMeans(bench_input))))
invisible(row_loop(bench_input))  # warm up before recording
invisible(rowMeans(bench_input))
timings <- matrix(NA_real_, 5, 2,
                  dimnames = list(NULL, c("loop", "rowMeans")))
for (k in seq_len(nrow(timings))) {
  timings[k, "loop"] <- system.time(row_loop(bench_input))[["elapsed"]]
  timings[k, "rowMeans"] <- system.time(rowMeans(bench_input))[["elapsed"]]
}

Read and report repeated timings

timings
     loop rowMeans
[1,] 0.01        0
[2,] 0.01        0
[3,] 0.00        0
[4,] 0.00        0
[5,] 0.01        0

Report dimensions, repetitions, R version, and variability. A displayed zero can mean the task is below the timer’s resolution, not that it costs no time.

Memory and the final recommendation

object.size(bench_input)
160216 bytes
object.size(rowMeans(bench_input))
8048 bytes

object.size() estimates an R object’s stored size. It does not measure peak memory or all temporary allocations during a calculation.

Recommend an implementation using correctness, stable shape, readability, and measured time. State when you would reconsider the choice.

Summary

  • Vectorize when the vector expression states the operation directly.
  • Use a loop when the algorithm has state or the steps need to remain explicit.
  • Preallocate output; repeated growth is the expensive pattern.
  • Prefer functionals with a stable output contract for repeated independent work.
  • Verify equivalence before benchmarking or optimizing.
