1 · What the machine is telling you

Two kinds of broken

It stops

Error in sum(x) :
  invalid 'type' (character) of argument

Loud. You know instantly. The location is roughly right. The worst case is that you lose an hour.

It finishes

[1] -7.88

Silent. A number, correctly formatted, plausible, and wrong. Nothing on screen distinguishes it from the right answer.

Almost everything in this session is aimed at the second column. The first column is a nuisance; the second column is how analyses get retracted.

The three conditions

R has exactly three, and they differ in what happens next:

check_dose <- function(mg) {
  message("checking ", length(mg), " doses")   # 1. carries on
  if (any(mg > 100)) warning("dose above 100 mg")  # 2. carries on
  if (any(mg < 0)) stop("negative dose")            # 3. stops here
  invisible(TRUE)
}

check_dose(c(10, 120, -5))
checking 3 doses
Warning in check_dose(c(10, 120, -5)): dose above 100 mg
Error in check_dose(c(10, 120, -5)): negative dose
Condition Execution Goes to Use it for
message() continues stderr Progress, and what you did
warning() continues stderr, often deferred “This is probably not what you meant”
stop() halts stderr “I cannot produce a correct answer”

Anatomy of an error message

mean(trial_raw$creat_raw)
Warning in mean.default(trial_raw$creat_raw): argument is not numeric or
logical: returning NA
[1] NA
sum(trial_raw$creat_raw)
Error in sum(trial_raw$creat_raw): invalid 'type' (character) of argument
Error in sum(trial_raw$creat_raw) : invalid 'type' (character) of argument
        └──────── where ────────┘   └──────────── what ─────────────────┘
  • Error in names the call that raised it — not necessarily the call that is wrong.
  • The text after the colon is R’s vocabulary, and it is small. invalid 'type', object not found, subscript out of bounds, non-numeric argument, argument of length zero. You will learn all of them this term.

Warnings are the ones that cost you

creat <- as.numeric(trial_raw$creat_raw)
Warning: NAs introduced by coercion
mean(creat)
[1] NA
sum(is.na(creat))
[1] 3
trial_raw$creat_raw[is.na(creat)]
[1] "NA"    "<0.30" "NA"

The warning told you the truth: three values could not be read. Two are genuinely missing. One is a real measurement — a below-limit-of-detection result — and you have just silently deleted it.

Where it stops is not where it broke

# Mean change in SBP, for a subgroup, rounded for the table.
mean_change <- function(data) summarise_change(data$change)
summarise_change <- function(x) round(pooled_mean(x), 1)
pooled_mean <- function(x) sum(x) / length(x)

site_3 <- subset(trial_raw, site == 3)
site_3$change <- as.character(site_3$change)  # ← the actual bug, 3 lines up

mean_change(site_3)
Error in sum(x): invalid 'type' (character) of argument

The error names sum(x). sum() is three function calls away from the mistake and did nothing wrong. The distance between the symptom and the cause is what makes debugging hard — and it is what traceback() exists to close.

2 · Isolating a minimal failing example

The procedure

The most valuable debugging skill, and the one nobody teaches:

  1. Reproduce it. From a clean session. If you cannot make it fail on demand, you cannot tell when you have fixed it.
  2. Cut the data down. 60 rows → 6 rows → 1 row. Does it still fail?
  3. Cut the code down. Delete a step. Still fails? Delete another.
  4. Keep cutting until removing anything makes the bug disappear. What is left is the bug.

Most of the time you never reach step 4. The bug becomes obvious somewhere in step 3, and you never find out how small the example could have been.

Cut the data down

Start from the failure, and make the input smaller:

mean_change(site_3)                 # 11 rows — fails
Error in sum(x): invalid 'type' (character) of argument
mean_change(site_3[1:3, ])          # 3 rows  — still fails
Error in sum(x): invalid 'type' (character) of argument
mean_change(site_3[1, ])            # 1 row   — still fails
Error in sum(x): invalid 'type' (character) of argument
pooled_mean(site_3$change[1])       # drop the wrappers entirely
Error in sum(x): invalid 'type' (character) of argument
site_3$change[1]                    # look at the value itself
[1] "-1"

One row still fails, so the bug is not about missingness, not about the subgroup, and not about n. It is about a single value — and the quotes on the last line are the answer.

Cut the code down

The other direction: keep the data, delete the pipeline.

# what you have — and it fails somewhere
report <- trial |>
  filter(!is.na(sbp_12), site %in% c(2, 3)) |>
  mutate(change = sbp_12 - sbp_0,
         responder = change <= -10,
         band = cut(age, breaks = quantile(age, c(0, .5, 1)))) |>
  group_by(arm, band) |>
  summarise(n = n(), pct = 100 * mean(responder), .groups = "drop")
# run it one verb at a time and look at the result of each
step1 <- trial |> filter(!is.na(sbp_12), site %in% c(2, 3))
nrow(step1)                                  # 0? then the filter is the bug
step2 <- step1 |> mutate(change = sbp_12 - sbp_0)
summary(step2$change)                        # all NA? then the mutate is

A pipeline is unusually hard to debug precisely because the intermediate results have no names. Breaking it apart is not a failure of style — it is the technique.

Bisection, and what it buys you

When you have no hypothesis at all, halve it:

  • Comment out the bottom half of the script. Does it still fail?
  • No → the bug is in the half you removed. Yes → it is in the half you kept.
  • Repeat. Two hundred lines becomes eight in about five steps.

The same move works on history rather than on code — git bisect finds the commit that introduced a bug by the same halving. Your session 2 habit of small commits is what makes it possible.

The minimal example you end up with is not a by-product. It is the test you add so the bug cannot come back, and the reprex you post if you still need help.

3 · traceback(), browser(), debug()

traceback()

Run it immediately after an error. It prints the call stack as it was when R gave up:

> mean_change(site_3)
Error in sum(x) : invalid 'type' (character) of argument

> traceback()
3: pooled_mean(x)
2: summarise_change(data$change)
1: mean_change(site_3)

Read it from the bottom up. Line 1 is what you typed. Line 3 is the last thing R was doing. The bug is somewhere on the way down.

traceback() shows the most recent error only, and only after a real error at the console. It has nothing to say inside a rendering document.

Reading a stack

The error is raised at the bottom. The cause entered at the top. traceback() gives you the path between them, which is the thing you cannot get any other way.

browser()

traceback() tells you where. browser() lets you look.

pooled_mean <- function(x) {
  browser()            # ← execution pauses here, with x available
  sum(x) / length(x)
}

mean_change(site_3)
Called from: pooled_mean(x)
Browse[1]> str(x)
 chr [1:11] "-2" "-14" "-25" "-9" ...
Browse[1]> class(x)
[1] "character"
Browse[1]> Q

Inside the browser you are in a normal R console, sitting inside the paused function. Every object in that frame is real and inspectable.

The browser commands

Key Does You want it when
n next — run this line, stop at the next Walking through the body
s step in — descend into the call on this line The suspect is the function being called
f finish — run to the end of this loop or function You stepped in by mistake
c continue — resume until the next browser() or the end You have seen enough
Q quit — abandon it, back to the console Almost always, at the end
where print the stack from here You have lost track of how deep you are

A variable called n, s, c, f or Q cannot be printed by typing its name — the browser reads it as a command. Use print(n).

debug(), debugonce(), and breakpoints

When you cannot edit the function — it is in a package, or it is 300 lines away:

debugonce(pooled_mean)   # browse the next call, then forget about it
mean_change(site_3)

debug(pooled_mean)       # browse EVERY call until you stop it
undebug(pooled_mean)     # ...which you must remember to do
Edit the file? Persists?
browser() in the body yes until you delete it
debugonce(f) no one call — the safe default
debug(f) no until undebug(f)
RStudio breakpoint no (stored by the IDE) until you click it off

options(error = recover)

The heavy tool. On any error, R offers you every frame in the stack and drops you into the one you choose:

options(error = recover)

mean_change(site_3)
Error in sum(x) : invalid 'type' (character) of argument

Enter a frame number, or 0 to exit

1: mean_change(site_3)
2: summarise_change(data$change)
3: pooled_mean(x)

Selection: 2
Called from: summarise_change(data$change)
Browse[1]> str(data$change)
 chr [1:11] "-2" "-14" "-25" ...

Turn it off with options(error = NULL). Never set it in a script or a .qmd.

Which tool, when

Situation Reach for
An error, and you do not know which function raised it traceback()
You know the function, and want to see its arguments browser() or debugonce()
The function is in a package debugonce(pkg::f)
No error, but the answer is wrong browser() + the minimal example
An error you cannot reproduce cheaply options(error = recover)
A warning and you want to know where from options(warn = 2), then traceback()
Anything at all, and you are in a hurry print() and str()

The last row is not a joke. Well-placed print() calls solve most bugs, and there is no shame in them.

4 · Fail fast, fail loud

Fail fast, fail loud

Session 11 gave you guard clauses. The argument is worth restating in this session’s terms:

  • A function that stops costs you ten minutes.
  • A function that returns a plausible wrong number costs you a paper.
# Responder rate: percentage of patients with a fall of at least 10 mmHg.
responder_rate <- function(change) {
  stopifnot(is.numeric(change))
  if (length(change) > 0 && all(is.na(change))) {
    stop("change is entirely missing", call. = FALSE)
  }

  n_obs <- sum(!is.na(change))
  100 * sum(change <= -10, na.rm = TRUE) / n_obs
}

responder_rate(as.character(trial$change))
Error in responder_rate(as.character(trial$change)): is.numeric(change) is not TRUE

stopifnot() outside a function

Assertions are not only for functions. Put them in the analysis where an assumption is made:

# One row per patient is assumed by every summary below.
stopifnot(!anyDuplicated(trial$id))

# The join in session 7 must not have created rows.
stopifnot(nrow(trial) == 60)

# Change must be derived, never imported.
stopifnot(all(trial$change == trial$sbp_12 - trial$sbp_0))

# And the one that actually fails:
stopifnot("no outcome may be missing" = !anyNA(trial_raw$sbp_12))
Error: no outcome may be missing

Each line is a sentence you would otherwise have written as a comment — except this one is checked every time the document renders.

Make the check permanent

You already built a minimal failing example. Do not throw it away.

# Known answers, worked out by hand, checked on every render.
stopifnot(
  "empty input gives NaN, not an error" =
    is.nan(responder_rate(numeric(0))),
  "a single responder gives 100" =
    responder_rate(-12) == 100,
  "a single non-responder gives 0" =
    responder_rate(-2) == 0,
  "missing values are excluded from the denominator" =
    responder_rate(c(-12, NA)) == 100
)
cat("all checks passed\n")
all checks passed

Four lines, and the fourth is the one the lab’s broken version fails. A test is just an example with a known answer, written down.

testthat, in one slide

When the project is big enough to want real tests:

library(testthat)

test_that("responder_rate handles missingness", {
  expect_equal(responder_rate(-12), 100)
  expect_equal(responder_rate(c(-12, NA)), 100)
  expect_error(responder_rate("a"), "is.numeric")
  expect_true(is.nan(responder_rate(numeric(0))))
})
Does
expect_equal(x, y) Equal within tolerance — the right choice for numbers
expect_identical(x, y) Exactly equal, type included
expect_error(f(), "text") The call fails, with a message matching "text"
expect_warning(), expect_true() As they read

Not installed on the course machines and not required here. Use stopifnot() — the idea is identical, and it is what the previous slide runs.

5 · Floating point

The slide that ruins everyone’s afternoon

0.1 + 0.2 == 0.3
[1] FALSE
0.1 + 0.2 - 0.3
[1] 5.551115e-17
print(0.1, digits = 22)
[1] 0.1000000000000000055511

R has not made a mistake. 0.1 is not 0.1 — it is the closest number to 0.1 that a 64-bit double can represent, and that number is slightly too big.

Binary cannot write one tenth

In base 10, ⅓ needs infinitely many digits: 0.3333…

In base 2, one tenth needs infinitely many digits: 0.0001100110011001100…

A double gets 53 bits for the value. So R stores the closest 53-bit truncation, which is off by about 1 part in 1016.

0.5 + 0.25 == 0.75    # exact: halves and quarters ARE representable
[1] TRUE
1 - 0.9 == 0.1        # not exact
[1] FALSE
0.3 - 0.1 == 0.2      # not exact
[1] FALSE

Integers up to 253 are exact. Halves, quarters, eighths are exact. Tenths are not — and clinical data is measured in tenths.

Machine epsilon

.Machine$double.eps
[1] 2.220446e-16

The smallest e such that 1 + e != 1. It is the width of the gap between representable numbers near 1 — and it is the unit in which “close enough” is measured.

1 + .Machine$double.eps == 1
[1] FALSE
1 + .Machine$double.eps / 2 == 1
[1] TRUE

The gap scales with magnitude. Near 1 it is 2 × 10-16; near 106 it is about 10-10; near 10-6 it is far smaller. Absolute tolerances that work for one scale are wrong for another — which is why all.equal() defaults to a relative one.

all.equal(), and the trap in it

all.equal(0.1 + 0.2, 0.3)
[1] TRUE
isTRUE(all.equal(0.1 + 0.2, 0.3))
[1] TRUE
all.equal(1, 2)          # NOT FALSE — a character description
[1] "Mean relative difference: 1"

all.equal() returns TRUE or a description of the difference. A non-empty string is truthy enough to break an if. Always wrap it: isTRUE(all.equal(x, y)).

Or compare by hand, when you know the scale you care about:

abs((0.1 + 0.2) - 0.3) < 1e-8
[1] TRUE

It is not only ==

schedule <- seq(0.1, 1.0, by = 0.1)   # titration steps, as a fraction
which(schedule == 0.3)                 # integer(0) — no such step
integer(0)
# Session 13's loop, accumulating a total dose.
total <- 0
for (i in 1:10) total <- total + 0.1
total == 1
[1] FALSE
print(total, digits = 18)
[1] 0.999999999999999889

== was never the risk on its own. Any equality test hidden inside something else carries it: which(), match(), %in%, switch(), a lookup table keyed on a decimal, duplicated(), and a while loop that stops “when the total reaches 1”.

Integer overflow

.Machine$integer.max
[1] 2147483647
x <- 2147483647L
x + 1L
Warning in x + 1L: NAs produced by integer overflow
[1] NA
x + 1        # a double: no overflow, but no longer exact either
[1] 2147483648

R’s integers are 32-bit and stop at about 2.1 billion. Doubles carry on, but above 253 they cannot represent every whole number — so a count can start skipping.

Why likelihoods are computed on the log scale

big <- rnorm(400, mean = 148, sd = 14)

prod(dnorm(big, 148, 14))        # the likelihood, directly
[1] 0
log(prod(dnorm(big, 148, 14)))   # ...and its log
[1] -Inf
sum(dnorm(big, 148, 14, log = TRUE))   # the same quantity, computed properly
[1] -1624.257

The true value is about 10-705. The smallest positive double is about 10-308, so the product underflows to exactly zero — and log(0) is -Inf. Summing logs never leaves the representable range.

The floating-point rules

Rule
Never == on computed doubles isTRUE(all.equal(x, y)), or abs(x - y) < tol
== is fine on integers and strings id == "P003", site == 3L
No floating-point keys, indices, or counters Use integers, derive the decimal
Identifiers are character Not numeric. colClasses at import
Likelihoods and probabilities live on the log scale dnorm(..., log = TRUE), then sum()
round() is for display It does not make a number exact
Report at the precision you measured Not at the precision R prints

6 · Habits that prevent debugging

suppressWarnings()

creat <- suppressWarnings(as.numeric(trial_raw$creat_raw))
mean(creat, na.rm = TRUE)
[1] 0.927193

This runs cleanly, produces a number, and has silently deleted a real measurement. The warning was the only thing standing between you and that result.

It has exactly one legitimate use: a warning you have read, diagnosed, and decided is not a problem — with a comment saying so.

# Sites 1-4 only; `site` is a factor with an unused level 5 from the CRF,
# which as.integer() warns about. Checked: no patient has site 5.
site_num <- suppressWarnings(as.integer(as.character(trial$site)))

Names and comments that debug for you

# what you cannot debug
x <- d[d$g == 1, ]
y <- mean(x$v, na.rm = TRUE)
z <- y * 0.1
# what you can
site_3 <- subset(trial, site == 3)
mean_weight_kg <- mean(site_3$weight_kg, na.rm = TRUE)

# Dose is 0.1 mg per kg of body weight (protocol v2, section 4.3).
mean_dose_mg <- mean_weight_kg * 0.1

The second version cannot have a unit bug hiding in it, because the units are in the names. The comment answers the question a reader would otherwise have to ask you — and “why 0.1” is not answerable from the code.

How to write a reprex

A reproducible example. Four requirements, and they are not negotiable:

  1. Self-contained — runs in a fresh session. Every library() included.
  2. Minimal — block 2’s procedure. Not your script.
  3. Data included — dput(head(x)), or a tiny made-up frame. Never “my data looks like this”.
  4. The actual output — the real error text, copied, not described.
library(dplyr)

d <- data.frame(id = c("P001", "P002"), sbp = c("148", "152"))

d |> summarise(mean_sbp = mean(sbp))
#> Warning: argument is not numeric or logical: returning NA
#>   mean_sbp
#> 1       NA

reprex::reprex() runs your clipboard in a clean session and formats it exactly like this. Most reprexes never get posted — you find the bug while building one.

Summary

  • Reproduce the failure before editing the code.
  • Reduce the data and code until the first broken assumption is visible.
  • Use the call stack, browser, and breakpoints to inspect state deliberately.
  • Assertions and small tests preserve a repair after today.
  • Finite-precision arithmetic requires tolerance-aware reasoning.
