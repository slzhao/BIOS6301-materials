What is one row?

Before you join anything, say out loud what one row of each table is. This is the table’s grain.

Table One row is Key
trial one patient id
sites one site site
labs one patient-visit id + week

A key is the set of columns that identifies a row uniquely. If it does not identify a row uniquely, it is not a key — it is just some columns.

Joining changes the grain unless you can prove it does not. Say what the grain of the result should be before you type the join.

Check the keys first

The check takes one line and it goes before the join, not after:

sites_dup |> count(site) |> filter(n > 1)
  site n
1    2 2
trial |> count(id) |> filter(n > 1)
[1] id n 
<0 rows> (or 0-length row.names)

An empty result is the answer you want: id is a key of trial.

count(key) |> filter(n > 1) is the single highest-value habit in this session. Run it on both tables, every time, before you join.

2 · The join family

Six joins, two kinds

Join Keeps Adds columns from y?
Mutating left_join(x, y) every row of x yes
inner_join(x, y) rows matched in both yes
right_join(x, y) every row of y yes
full_join(x, y) every row of either yes
Filtering semi_join(x, y) rows of x with a match no
anti_join(x, y) rows of x without a match no

The split is the useful thing here. A mutating join changes the columns and may change the rows. A filtering join changes only the rows — it is filter() with the condition stored in another table.

Which join do you want?

The base R way

merge(trial, sites, by = "site", all.x = TRUE)

inner_join(): rows that vanish

nrow(inner_join(trial, sites, by = "site"))
[1] 45

Fifteen patients are gone, and the result does not say so.

inner_join(trial, sites, by = "site") |>
  count(arm)
        arm  n
1   Placebo 20
2 Treatment 25

An inner_join() is a silent exclusion criterion. If the rows it drops are not missing at random — and site is never missing at random — your analysis population has changed and your table 1 will not match your consort diagram.

anti_join(): the diagnostic

Which patients failed to match?

anti_join(trial, sites, by = "site") |>
  count(site)
  site  n
1    4 15

And in the other direction — which sites have no patients?

anti_join(sites, trial, by = "site")
  site site_name n_beds
1    5 Satellite     44

Run anti_join() both ways after every join you care about. It costs two lines and it is the difference between knowing your data and hoping.

The other three

c(left  = nrow(left_join(trial, sites, by = "site")),
  inner = nrow(inner_join(trial, sites, by = "site")),
  right = nrow(right_join(trial, sites, by = "site")),
  full  = nrow(full_join(trial, sites, by = "site")),
  semi  = nrow(semi_join(trial, sites, by = "site")),
  anti  = nrow(anti_join(trial, sites, by = "site")))
 left inner right  full  semi  anti 
   60    45    46    61    45    15
  • full_join gives 61 — the 60 patients plus one all-NA patient row carrying site 5.
  • right_join(x, y) is left_join(y, x) with the columns in a different order. Use left_join and swap the arguments — then the table your analysis is about is always on the left.
  • semi_join gives 45 rows and the same columns as trial. Compare with inner_join, which gives 45 rows and three more columns.

3 · Predicting the row count

The only rule you need

For each row of x, count how many rows of y share its key. Add those counts up. That is the number of rows a mutating join returns.

Multiplicity in y Rows out (left_join) Name
exactly one for every x row nrow(x) one-to-one
at most one, sometimes none nrow(x) many-to-one
several for some x rows more than nrow(x) one-to-many
several on both sides many more many-to-many

A left_join() never loses rows. It very much can gain them. Those are two different facts and students conflate them constantly.

Many-to-one: the safe case

sites has at most one row per site, so 60 rows in, 60 rows out.

nrow(trial)
[1] 60
nrow(left_join(trial, sites, by = "site"))
[1] 60

We are entitled to expect that only because we checked:

sites |> count(site) |> filter(n > 1)
[1] site n   
<0 rows> (or 0-length row.names)

Most joins you write should be many-to-one: many patients, one lookup row each. When a join is supposed to be many-to-one and is not, you have found a data error — not a join problem.

One-to-many: rows multiply on purpose

labs has two rows per patient — baseline and Session 12.

nrow(labs)
[1] 120
trial_labs <- left_join(trial, labs, by = "id")
nrow(trial_labs)
[1] 120

60 × 2 = 120, predicted before running it.

head(trial_labs[, c("id", "arm", "week", "creat")], 4)
    id     arm week creat
1 P001 Placebo    0  1.13
2 P001 Placebo   12  1.15
3 P002 Placebo    0  1.26
4 P002 Placebo   12  1.15

This is correct and often exactly what you want — the result’s grain is now one row per patient-visit. But every patient-level column is now repeated, so mean(trial_labs$age) is a weighted mean, not a patient mean.

Many-to-many: rows multiply by accident

sites_dup is sites with one row pasted in twice.

nrow(left_join(trial, sites_dup, by = "site"))
Warning in left_join(trial, sites_dup, by = "site"): Detected an unexpected many-to-many relationship between `x` and
`y`.
i Row 6 of `x` matches multiple rows in `y`.
i Row 1 of `y` matches multiple rows in `x`.
i If a many-to-many relationship is expected, set `relationship =
  "many-to-many"` to silence this warning.
[1] 78

Site 2 has 18 patients. 60 + 18 = 78.

Eighteen patients are now in the data twice. Every count, every mean, every model is wrong — and the only visible symptom is a row count that nobody looked at.

Predict, then check

Write the prediction into the code. It costs one line:

joined <- left_join(trial, sites, by = "site")
stopifnot(nrow(joined) == nrow(trial))
joined_bad <- left_join(trial, sites_dup, by = "site")
stopifnot(nrow(joined_bad) == nrow(trial))
Error: nrow(joined_bad) == nrow(trial) is not TRUE

stopifnot() is session 12 material — borrowed here as a one-liner. It does nothing when the condition holds and stops the render when it does not, which is exactly what you want from an assumption.

4 · Safety rails

The relationship argument

State what you believe, and let the join enforce it:

left_join(trial, sites_dup, by = "site", relationship = "many-to-one")
Error in `left_join()`:
! Each row in `x` must match at most 1 row in `y`.
i Row 6 of `x` matches multiple rows in `y`.

Four values: "one-to-one", "one-to-many", "many-to-one", "many-to-many". The last one is not a safety rail — it is how you tell dplyr you meant it, and it silences the warning.

The unmatched argument

left_join(trial, sites, by = "site", unmatched = "error")
Error in `left_join()`:
! Each row of `y` must be matched by `x`.
i Row 4 of `y` was not matched.

Read the message carefully. For a left_join(), rows of x are never dropped — so unmatched= guards the only side that can lose rows: y. It just told us site 5 is unused.

To assert that every patient matched, use the diagnostic:

nrow(anti_join(trial, sites, by = "site")) == 0
[1] FALSE

The join checklist

Five lines. Every join that matters.

# 1. What is the grain of each table, and of the result?
# 2. Duplicate keys?
sites |> count(site) |> filter(n > 1)
# 3. Predict the row count. Write the number down.
# 4. Join, asserting the relationship.
joined <- left_join(trial, sites, by = "site",
                    relationship = "many-to-one")
# 5. What failed to match, both ways?
anti_join(trial, sites, by = "site")
anti_join(sites, trial, by = "site")

Steps 2 and 5 belong in your document, not your console. They are part of the analysis: they are how a reader knows the join was safe.

5 · Head to head: merge()

merge() anatomy

merge(x, y,
      by      = NULL,       # key columns, in BOTH tables
      by.x    = ,  by.y = , # when the key has different names
      all.x   = FALSE,      # keep unmatched rows of x?
      all.y   = FALSE,      # keep unmatched rows of y?
      all     = FALSE,      # shorthand for both
      suffixes = c(".x", ".y"),
      sort    = TRUE)       # sorts the result by the key

Everything a join can do is a combination of all.x and all.y. There is no how = "left" argument; the two logicals are the join type.

6 · Reshaping

The same data, two shapes

Wide — one row per patient

    id     arm sbp_0 sbp_6 sbp_12
1 P001 Placebo   160   146    144
2 P002 Placebo   162   165    156
3 P003 Placebo   157   151    156

One column per timepoint. Good for reading, for table 1, for a paired t-test.

Long — one row per patient-visit

    id     arm week sbp
1 P001 Placebo    0 160
2 P001 Placebo    6 146
3 P001 Placebo   12 144
4 P002 Placebo    0 162
5 P002 Placebo    6 165
6 P002 Placebo   12 156

Timepoint is a value in a column. Good for plotting, grouping, and mixed models.

Same 180 numbers. 60 × 3 cells becomes 180 × 1 column.

Which shape do you need?

You want to Shape
Read the data as a human wide
A baseline characteristics table wide
sbp_12 - sbp_0 wide
Plot outcome against time long
A summary at each timepoint long
Fit a mixed model or GEE long
Send it to a clinical collaborator wide, always

Reshaping is not a step in a pipeline you do once. It is a thing you do back and forth, several times, in a single analysis.

pivot_wider() and the round trip

sbp_long |>
  pivot_wider(
    names_from   = week,
    values_from  = sbp,
    names_prefix = "sbp_"
  )

pivot_wider() is the inverse. It needs to know which column supplies the new names and which supplies the new values; everything else becomes the identifier.

If the id columns plus names_from do not identify a row uniquely, pivot_wider() cannot put one value in one cell — so it puts a list in the cell and warns. That warning means you have duplicate measurements, which is a data question, not a code question.

Base reshape(): recognition only

sbp_long <- reshape(wide3,
  direction = "long",
  idvar     = "id",
  varying   = list(c("sbp_0", "sbp_6", "sbp_12")),
  v.names   = "sbp",
  timevar   = "week",
  times     = c(0, 6, 12))
dim(sbp_long)
[1] 180   4
back <- reshape(sbp_long, direction = "wide", idvar = "id",
                timevar = "week", v.names = "sbp", sep = "_")
dim(back)
[1] 60  5

reshape() works, and it round-trips exactly. The idvar / timevar / varying interface is genuinely punishing, it is easy to get subtly wrong, and pivot_longer() is the tool you will actually use. Learn to recognise this call. Do not learn to write it.

7 · Window functions

Within patient, in order

lag() looks back one row. group_by() says back within what.

visits <- sbp_long |>
  arrange(id, week) |>
  group_by(id) |>

    prev_sbp = lag(sbp),
    change   = sbp - lag(sbp)

Summary

  • State the grain and keys of every table before joining.
  • Predict row counts and detect duplicate keys before the join.
  • Use anti-joins to inspect unmatched records in both directions.
  • Wide and long forms encode different observation units.
  • Order explicitly before lagged or cumulative operations.
