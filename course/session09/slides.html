What feels different from RStudio

  • Editor foundation: Positron uses Code OSS, the foundation of VS Code, with extensions and flexible layouts.
  • Language sessions: select and manage R or Python interpreters within the workspace. RStudio’s workflow centers on R, with Python integration.
  • Commands: the Command Palette is a frequent starting point for actions that you may know as RStudio buttons.
  • Projects: open a folder as a Positron workspace. Keep the .Rproj file for RStudio, but do not expect its settings to transfer automatically.

Positron’s VS Code foundation

Positron builds on Code OSS, the open-source core of Visual Studio Code. Posit adds the R/Python Console, Variables, Plots, and Data Explorer.

  • VS Code serves a much broader developer community across many languages.
  • Its extension ecosystem offers a wide choice of AI assistants and advanced tools for debugging, Git, databases, testing, and remote development.
  • Positron can reuse many compatible extensions while providing a ready-made environment for data science.

Why this matters: a larger ecosystem means more options for extending your workflow. Availability and compatibility still depend on the specific tool.

Start with a familiar chat conversation

If you have used ChatGPT to ask a question, start with that pattern:

Here is my R code. Why does it return NA? Explain how to fix it.

You supply context, read the answer, ask follow-up questions, and check it.

Inside a coding environment, two things can change:

  • Context: an assistant may read selected files or session information.
  • Actions: some workflows can insert code, edit files, or run commands.

Before using a tool, identify both what it can see and what it can do.

One R problem, three different needs

x <- c(4, 6, 8, NA)

What you need now A suitable starting point
“I do not understand why this is NA.” Chat: ask for an explanation
“I understand missing values. Help me finish the line.” Inline: complete code at the cursor
“Update my saved script and add checks.” Agent: delegate a bounded change

The task is similar. Your immediate goal determines the form of help.

Chat: what a useful answer should explain

For x <- c(4, 6, 8, NA), check these claims:

  • mean(x) returns NA because a value is missing.
  • mean(x, na.rm = TRUE) uses the three observed values and returns 6.
  • na.rm = TRUE changes this calculation. It does not remove an entry from x.

Follow-up question: “Does this change x? How can I check?”

Agent example: verify the saved result

A suitable final script is:

x <- c(4, 6, 8, NA)
mean_x <- mean(x, na.rm = TRUE)
stopifnot(length(x) == 4L)
stopifnot(sum(!is.na(x)) == 3L)
stopifnot(isTRUE(all.equal(mean_x, 6)))
print(mean_x)

Review Source Control: only the intended analysis file changed, and x still includes NA. Run from a fresh R session. Expect 6 and no failed assertions.

The expected values came from our calculation before the agent wrote the checks.

From code assistance to statistical verification

Next: can we tell when plausible code answers the wrong statistical question?

Our next example summarizes a measurement by treatment arm. The key issue is the denominator when values are missing.

Give statistical context in the source

# At week 4, report total n, observed n, mean marker,
# and SD by randomized arm. Do not remove missing rows
# before counting total n.

A precise comment improves the proposed code and remains useful documentation even when Copilot is disabled.

Vague instructions invite hidden choices

# Summarize marker by group.

Compare with:

# At week 4, retain all randomized participants and report
# total n, observed n, mean, and SD by arm.

The second comment specifies population, time, denominator, statistics, and grouping.

Plausible code can answer the wrong question

visit |>
  dplyr::filter(week == 4, !is.na(marker)) |>
  dplyr::summarise(
    n = dplyr::n(),
    mean_marker = mean(marker),
    sd_marker = sd(marker),
    .by = arm
  )

The code runs, but n is observed n, not total n, because missing rows were removed first.

Predict before running

For the proposed pipeline, write down:

  1. Which rows survive the filter?
  2. What will n() count?
  3. Can an arm with more missing outcomes appear to have a smaller sample?
  4. Which requested quantity is absent?

Repair the statistical meaning

visit |>
  dplyr::filter(week == 4) |>
  dplyr::summarise(
    n_total = dplyr::n(),
    n_observed = sum(!is.na(marker)),
    mean_marker = mean(marker, na.rm = TRUE),
    sd_marker = sd(marker, na.rm = TRUE),
    .by = arm
  )

The correction follows from the estimand and denominator—not from asking for more fluent-looking code.

A verification ladder

Level Question Example evidence
Syntax Did it run? no error or warning
Data Did it use the intended rows? counts and key checks
Statistical Did it estimate the intended quantity? denominator and missingness review
Reproducibility Does it work from source? restart and render/run all

Passing a lower level does not imply passing the next one.

Five verification questions

  1. What does one input row represent?
  2. Which rows and columns did the code use?
  3. How did it handle missing values?
  4. What does one output row and denominator represent?
  5. Can I verify one result independently?

Independent checks should be small

week4 <- visit[visit$week == 4, ]
with(week4, table(arm, useNA = "ifany"))
with(week4, tapply(!is.na(marker), arm, sum))

Do not ask Copilot to generate both the answer and its only verification.

Other common failures

  • joining without checking duplicate keys;
  • silently removing missing observations;
  • using an unexpected denominator;
  • inventing a function or argument;
  • changing a working style more broadly than requested;
  • producing a plot whose labels do not match its calculation.

Good first uses are small and checkable

  • complete a familiar function call;
  • draft repetitive column names or plotting labels;
  • translate one already-understood base-R operation to dplyr;
  • propose a test case for an existing function;
  • explain an error message using synthetic context.

Avoid beginning with a full analysis whose answer you cannot independently describe.

Context creates a privacy boundary

AI completion can use surrounding code and open-file context. Never expose:

  • protected health information or identifiable records;
  • restricted or confidential research data;
  • passwords, tokens, private keys, or .Renviron;
  • unpublished confidential material not approved for the service.

Use only synthetic course data in this session.

Course policy after today

  • AI coding assistance is allowed for homework and labs unless designated unaided.
  • Copilot is our example; the same rules apply to other AI tools.
  • Students remain responsible for every submitted line.
  • Important results and data decisions must be verified.
  • Substantive assistance must be disclosed.
  • AI assistance is not permitted on any examination.

Keep disclosure short and useful

AI use: I used GitHub Copilot to suggest the group-summary code. I corrected its
missing-value handling and verified the group counts independently.

Or:

AI use: None.
