Join keys

The by argument tells R which values identify a match.

patient_lookup |> count(id) |> filter(n > 1)

marker_wide |> count(id) |> filter(n > 1)

Zero rows here means no repeated IDs in that table.

A visit-level table can contain repeated IDs legitimately. Its row identifier would also need a visit variable.

Three joins for today’s work

Question Function
Keep all measurement rows and add metadata left_join()
Keep only participants appearing in both tables inner_join()
Find measurement rows without metadata anti_join()

left_join(x, y, by = "id") starts with x and matches its IDs against y.

A short join checklist

  • What does one row represent in each input?
  • Which columns identify the intended match?
  • Does the lookup have repeated keys?
  • How many rows remain, and which IDs failed to match?

before  after 
     4      4

Here the lookup ID is unique, so four measurement rows stay four.

Optional: Six joins, two kinds

Join Keeps Adds columns from y?
Mutating left_join(x, y) every row of x yes
inner_join(x, y) rows matched in both yes
right_join(x, y) every row of y yes
full_join(x, y) every row of either yes
Filtering semi_join(x, y) rows of x with a match no
anti_join(x, y) rows of x without a match no

The split is the useful thing here. A mutating join changes the columns and may change the rows. A filtering join changes only the rows — it is filter() with the condition stored in another table.

  • full_join gives 61 — the 60 patients plus one all-NA patient row carrying site 5.
  • right_join(x, y) is left_join(y, x) with the columns in a different order. Use left_join and swap the arguments — then the table your analysis is about is always on the left.
  • semi_join gives 45 rows and the same columns as trial. Compare with inner_join, which gives 45 rows and two more columns.

Optional: Row counts in an equality join

For each row of x, let m be its number of matches in y.

Join Rows contributed by that row of x
inner_join() m
left_join() max(1, m)

Add these contributions across x. An unmatched left-hand row contributes one row to a left join, with missing values in the added columns.

Optional: Relationships depend on both directions

Expected relationship Match limit
one-to-one Each row on either side matches at most one on the other
many-to-one Each x row matches at most one y row
one-to-many Each y row matches at most one x row
many-to-many Multiple matches can occur in both directions

Many patients can share a site. A unique site lookup therefore supports a many-to-one patient-to-site join.

Optional: Many-to-one: the safe case

sites has at most one row per site, so 60 rows in, 60 rows out.

nrow(trial)
[1] 60
nrow(left_join(trial, sites, by = "site"))
[1] 60

We are entitled to expect that only because we checked:

sites |> count(site) |> filter(n > 1)
[1] site n   
<0 rows> (or 0-length row.names)

A common lookup task is many-to-one: many patients, one lookup row each. When a join is supposed to be many-to-one and is not, you have found a data error — not a join problem.

Optional: One-to-many: rows multiply on purpose

labs has two rows per patient — baseline and week 12.

nrow(labs)
[1] 120
trial_labs <- left_join(trial, labs, by = "id")
nrow(trial_labs)
[1] 120

60 × 2 = 120, predicted before running it.

head(trial_labs[, c("id", "arm", "week", "creat")], 4)
    id     arm week creat
1 P001 Placebo    0  1.13
2 P001 Placebo   12  1.15
3 P002 Placebo    0  1.26
4 P002 Placebo   12  1.15

This is correct and often exactly what you want — the result’s grain is now one row per patient-visit. But every patient-level column is now repeated. A mean on this table weights patients by their visit counts. Here everyone has two visits, so it equals the patient-level mean.

Optional: Many-to-many: rows multiply by accident

sites_dup contains two conflicting records for site 2 (240 versus 245 beds).

`y`.

Eighteen patients are now in the data twice. Patient counts are inflated and summaries or models can change — and the only visible symptom is a row count that nobody looked at.

Optional: Predict, then check

Write the prediction into the code. It costs one line:

joined <- left_join(trial, sites, by = "site")
stopifnot(nrow(joined) == nrow(trial))
joined_bad <- left_join(trial, sites_dup, by = "site")
stopifnot(nrow(joined_bad) == nrow(trial))
Error: nrow(joined_bad) == nrow(trial) is not TRUE

stopifnot() is session 12 material — borrowed here as a one-liner. It does nothing when the condition holds and stops the render when it does not, which is exactly what you want from an assumption.

Optional: The relationship argument

State what you believe, and let the join enforce it:

left_join(trial, sites_dup, by = "site", relationship = "many-to-one")
Error in `left_join()`:
! Each row in `x` must match at most 1 row in `y`.
i Row 6 of `x` matches multiple rows in `y`.

Four values: "one-to-one", "one-to-many", "many-to-one", "many-to-many". The last one is not a safety rail — it is how you tell dplyr you meant it, and it silences the warning.

Optional: The unmatched argument

left_join(trial, sites, by = "site", unmatched = "error")
Error in `left_join()`:
! Each row of `y` must be matched by `x`.
i Row 4 of `y` was not matched.

Read the message carefully. For a left_join(), rows of x are never dropped — so unmatched= guards the only side that can lose rows: y. It just told us site 5 is unused.

To assert that every patient matched, use the diagnostic:

nrow(anti_join(trial, sites, by = "site")) == 0
[1] FALSE

Optional: merge() arguments

# Same key name in both tables:
merge(trial, sites, by = "site", all.x = TRUE)

# Different key names:
merge(trial, site_lookup,
      by.x = "site", by.y = "site_code", all.x = TRUE)
  • all.x = TRUE: keep unmatched rows from x.
  • all.y = TRUE: keep unmatched rows from y.
  • all = TRUE: keep unmatched rows from both.
  • sort = TRUE is the default.

tidyr and data shape

What is tidyr?

tidyr helps organize data into a usable table:

  • Each variable has a column.
  • Each observation has a row.
  • Each cell holds one value.

Today: pivot_longer() and pivot_wider().

Other tidyr tools split columns or make missing rows explicit. They are optional here.

Wide measurements

marker_wide
# A tibble: 4 x 3
  id    marker_w0 marker_w4
  <chr>     <dbl>     <dbl>
1 P01         4.1       4.4
2 P02         5.2       4.7
3 P03         6         5.1
4 P05         4.8       4.9

One row per participant. marker_w0 and marker_w4 store the same measurement at different weeks.

To summarize by week, it helps to give week its own column.

Wide to long with pivot_longer

marker_long <- marker_wide |>
  pivot_longer(
    cols = starts_with("marker_w"),
    names_to = "week",
    names_prefix = "marker_w",
    values_to = "marker"
  ) |>
  mutate(week = as.integer(week))

The column names supply week. The cell values supply marker.

stringr: text columns

Text differences that affect matching

raw_patients |> select(id, arm)
# A tibble: 4 x 2
  id      arm        
  <chr>   <chr>      
1 " p01 " " Control "
2 "p02"   "TREATED"  
3 " P03"  " treated "
4 "p04 "  "control"  
" p01 " == "P01"
[1] FALSE

Our study’s documented ID convention is uppercase with no surrounding spaces. The raw export does not consistently follow it.

Spaces and capitalization

str_trim("  Repeat   visit ")
[1] "Repeat   visit"
str_squish("  Repeat   visit ")
[1] "Repeat visit"
str_to_lower("TREATED")
[1] "treated"
str_to_upper("p01")
[1] "P01"

str_trim() removes outer spaces. str_squish() also reduces internal whitespace to one space.

Cleaning inside mutate

patients_text <- raw_patients |>
  mutate(
    id = str_to_upper(str_trim(id)),
    arm = str_to_lower(str_squish(arm)),
    note = str_to_lower(str_squish(note))
  )

Keep raw_patients unchanged so the original values remain available.

forcats: factors

Factor labels and level order

Session 4 introduced factor(), levels(), and relevel().

forcats provides functions for the same kinds of categorical-data tasks.

arm_factor <- factor(
  patients_text$arm, levels = c("treated", "control")
)
arm_factor
[1] control treated treated control
Levels: treated control

Each participant has a category. The factor also stores an order of levels.

fct_relevel changes the level order

arm_ordered <- fct_relevel(arm_factor, "control")
levels(arm_ordered)
[1] "control" "treated"
as.character(arm_factor) == as.character(arm_ordered)
[1] TRUE TRUE TRUE TRUE

The participant labels stay the same.

Under the usual treatment contrasts, the first level is the model reference.

For a full order: fct_relevel(x, "c", "b", "a").

fct_recode changes the labels

arm_labeled <- fct_recode(
  arm_ordered,
  Control = "control",
  Treatment = "treated"
)
arm_labeled
[1] Control   Treatment Treatment Control  
Levels: Control Treatment

The syntax is new_label = "old_label". This deliberately changes category labels, rather than only their order.

Factor operations inside mutate

patients_factor <- patients_text |>
  mutate(
    arm = fct_recode(arm,
      Control = "control", Treatment = "treated"),
    arm = fct_relevel(arm, "Control")
  )
patients_factor |> count(arm)
# A tibble: 2 x 2
  arm           n
  <fct>     <int>
1 Control       2
2 Treatment     2

fct_recode() can accept a character column and returns a factor.

Frequency order for a display

reported_site <- factor(c("East", "West", "West", "West", "East"))
levels(fct_infreq(reported_site))
[1] "West" "East"

fct_infreq() puts the most frequent level first.

Useful for displays. Use a deliberate scientific reference category for modeling.

lubridate: dates

Date parsers describe the input order

ymd("2026-10-18")
[1] "2026-10-18"
mdy("10/18/2026")
[1] "2026-10-18"
dmy("18/10/2026")
[1] "2026-10-18"

All three represent October 18, 2026.

Choose the parser using the source’s date convention.

An ambiguous date still needs a decision

mdy("03/04/2026")
[1] "2026-03-04"
dmy("03/04/2026")
[1] "2026-04-03"

Both conversions succeed, but they mean different days.

A parser cannot tell you which convention the data producer intended.

Parsing a column and extracting components

patients_clean <- patients_factor |>
  mutate(
    enrolled_date = ymd(enrolled),
    enrolled_year = year(enrolled_date),
    enrolled_month = month(enrolled_date)
  )

The original text column remains available for checking.

Dates and their components

patients_clean |>
  select(id, enrolled_date, enrolled_month)
# A tibble: 4 x 3
  id    enrolled_date enrolled_month
  <chr> <date>                 <dbl>
1 P01   2026-09-01                 9
2 P02   2026-09-03                 9
3 P03   2026-10-01                10

enrolled_date contains Date values. enrolled_month contains month numbers.

A check after date conversion

patients_clean |>
  filter(is.na(enrolled_date)) |>
  select(id, enrolled)
# A tibble: 0 x 2
# i 2 variables: id <chr>, enrolled <chr>

Zero rows means no missing parsed dates in this example.

Also inspect the range and whether the dates make sense for the study. A successful parse alone does not establish correctness.

Summary

  • dplyr joins match records by keys.
  • tidyr pivots change how measurements occupy rows and columns.
  • stringr cleans and searches text.
  • forcats distinguishes relabeling from level ordering.
  • lubridate parses dates using a known input convention.

Optional: What does change compare?

For each participant, after arrange(id, week):

Expression Meaning
marker - lag(marker) Change since the previous recorded row
marker - first(marker) Change from the first recorded row

The first recorded row is baseline only if baseline is present. With irregular visits, a previous-row change is not automatically a four-week change.
