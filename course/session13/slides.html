Three ways to say “for each”

Looks like Gives you
Loop for (v in outcomes) { ... } Nothing. You manage the result yourself
Apply family lapply(outcomes, f) A list, one element per input
purrr map(outcomes, f) A list, with a stricter contract
Vectorized sqrt(x), x > 140 The answer, with no iteration written at all

The first three are the same idea with different bookkeeping. The fourth is a different idea, and where it applies it beats all of them.

2 · for, while, and pre-allocation

Anatomy of a for loop

for (v in outcomes) {
  cat(v, ":", round(mean(trial[[v]]), 1), "mmHg\n")
}
sbp_0 : 149.5 mmHg
sbp_6 : 144 mmHg
sbp_12 : 141.6 mmHg
  • v takes each element of outcomes in turn. It is a real variable and it survives the loop.
  • trial[[v]] — double brackets, because v holds a name, not a column.
  • This loop prints. It does not produce an object. That is the next slide, and it is where the trouble is.

Pre-allocate, do not grow

Same answer, two ways. Watch the clock.

grow <- function(k) {
  out <- c()                                  # grows on every iteration
  for (i in seq_len(k)) out <- c(out, sqrt(i))
  out
}

prealloc <- function(k) {
  out <- numeric(k)                           # the right size, once
  for (i in seq_len(k)) out[i] <- sqrt(i)
  out
}

system.time(grow(50000))["elapsed"]
elapsed 
   5.14 
system.time(prealloc(50000))["elapsed"]
elapsed 
      0

Why growing is quadratic

out <- c(out, x) does not append. It allocates a new vector and copies the old one into it, every single iteration.

k seconds
20000 0.96
40000 3.44
80000 13.25

Doubling k costs roughly four times as much. Building a vector of length k this way copies about k²/2 values.

rbind()-ing rows onto a data frame inside a loop is the same bug, and worse — a data frame copy is far more expensive than a vector copy.

seq_along(), and the empty-vector trap

sbp <- numeric(0)          # a filter that matched nobody
1:length(sbp)
[1] 1 0
for (i in 1:length(sbp)) {
  cat("iteration", i, "gives value:", sbp[i], "\n")
}
iteration 1 gives value: NA 
iteration 0 gives value:  
seq_along(sbp)             # the fix: length zero means zero iterations
integer(0)

while: when you do not know how many

# Newton's method for sqrt(2): iterate until the step is small enough.
x    <- 1
iter <- 0

while (abs(x^2 - 2) > 1e-10 && iter < 100) {
  x    <- x - (x^2 - 2) / (2 * x)
  iter <- iter + 1
}

c(root = x, iterations = iter)
      root iterations 
  1.414214   4.000000

Always bound the loop. iter < 100 is not decoration — without it, a condition that never becomes false hangs your session with no error and no output.

3 · What “vectorized” actually means

The loop is still there. It is in C

“Vectorized” does not mean no loop. It means the loop is not written in R.

for loops are not slow. Growing is

y  <- rnorm(5e5)
tt <- \(expr) system.time(expr)[["elapsed"]]      # seconds, unnamed

c(`for loop`   = tt({
                   out <- numeric(length(y))
                   for (i in seq_along(y)) out[i] <- y[i]^2
                 }),
  `vapply()`   = tt(vapply(y, \(v) v^2, numeric(1))),
  `vectorized` = tt(y^2))
  for loop   vapply() vectorized 
      0.01       0.23       0.00

The functional is not faster than the loop — it is often slower. Only the last row is a different kind of thing.

The vectorized answers you already have

Instead of looping to… Write
build a new column from an old one trial$high <- trial$sbp_0 > 140
choose per row ifelse(), if_else(), case_when()
total or average a column sum(), mean(), cumsum()
average across visits, per patient rowMeans(), rowSums()
average one visit, across patients colMeans(), colSums()
element-wise max of two vectors pmax(), pmin()
count each value table()
test membership x %in% y
find where a condition holds which()
running total cumsum(), cumprod(), cummax()

Before writing a loop, ask whether a function already does it. Ten minutes of searching beats an hour of debugging an index.

# and when the function is mean or sum, do not use apply() at all
rowMeans(sbp_mat)   colMeans(sbp_mat)   # written in C, much faster

apply() on a data frame: the coercion trap

apply(trial[, c("id", "sbp_0", "sbp_12")], 1, max) |> head(4)
[1] "P001" "P002" "P003" "P004"

Those are patient IDs, not blood pressures. apply() needs a matrix, so it called as.matrix() — and a matrix holds one type, so every number became "P001"-style text.

Session 3’s coercion rules, arriving through a new door. apply() on a data frame with any character column silently converts everything to character.

mapply() and Map(): two vectors at once

When you need to walk two things in parallel:

labels <- c("Baseline", "6 weeks", "12 weeks")

mapply(
  \(col, lab) sprintf("%s: %.1f mmHg", lab, mean(trial[[col]])),
  outcomes, labels
)
                 sbp_0                  sbp_6                 sbp_12 
"Baseline: 149.5 mmHg"  "6 weeks: 144.0 mmHg" "12 weeks: 141.6 mmHg"

Map() is the same thing without simplification — it is to mapply() what lapply() is to sapply(), and it is the safer default.

5 · Head to head: base and purrr

map() is lapply() with better manners

base R

res <- lapply(trial[outcomes],
              summary_of)
res$sbp_12
    n  mean    sd 
 60.0 141.6  15.1

purrr

library(purrr)

res <- map(trial[outcomes],
           summary_of)
res$sbp_12

Same idea, same result. map() puts the data first — so it pipes — and is the only member of a family whose names all mean something.

purrr is not installed in this container, so the right-hand column is shown, not run. Everything on the left is live.

The \(x) shorthand

\(x) is base R 4.1, not tidyverse. It works everywhere a function does.

vapply(trial[outcomes], \(x) round(mean(x), 1), numeric(1))

 149.5  144.0  141.6 
# One t-test per outcome, in one line.
vapply(outcomes, \(v) t.test(trial[[v]] ~ trial$arm)$p.value, numeric(1)) |>
  signif(3)
  sbp_0   sbp_6  sbp_12 
0.63600 0.01490 0.00099 
# purrr, with the same shorthand and its own ~ .x form
map_dbl(outcomes, \(v) t.test(trial[[v]] ~ trial$arm)$p.value)
map_dbl(outcomes, ~ t.test(trial[[.x]] ~ trial$arm)$p.value)

map2(), pmap(), and the rest

Job base R purrr
Two vectors in parallel mapply(f, x, y) / Map(f, x, y) map2(x, y, f)
Many vectors in parallel mapply(f, x, y, z) pmap(list(x, y, z), f)
Side effects only — plots, files for / invisible(lapply()) walk(x, f)
Element and its name mapply(f, x, names(x)) imap(x, f)

Fail softly, keep going try() inside the function possibly(f, NA)

Note the argument order: purrr is data first, function second, always. Base R is not.

The same job, twice

Task. For every outcome, the treatment-minus-placebo difference in means.

vapply(outcomes, \(v) {
  m <- tapply(trial[[v]],
              trial$arm, mean)
  round(m[["Treatment"]] -
        m[["Placebo"]], 1)
}, numeric(1))
 sbp_0  sbp_6 sbp_12 
  -1.5   -9.4  -12.4 
map_dbl(outcomes, \(v) {
  trial |>
    group_by(arm) |>
    summarise(m = mean(.data[[v]])) |>
    pull(m) |>
    diff() |>
    round(1)
}) |> set_names(outcomes)

Same numbers. vapply() names its result for free; map_dbl() needs set_names(). And v holds a string, so it is .data[[v]] — not last week’s curly-curly, which wants a bare column name.

6 · Choosing, and when a loop is right

Which one do I want?

If… Use
A vectorized function already exists That function. Nothing else is close
One value per element, type known vapply() / map_dbl()
Results have different shapes lapply() / map()
You are looping for a side effect for loop, or walk()
Step i depends on step i−1 for or while. No functional can help
You are exploring at the console Whatever is quickest to type

Readability is the tie-breaker, not speed. Slide 16 showed that the timing difference between a loop and a functional is usually noise.

The loop you cannot remove

Iterative dependence: step i needs the result of step i−1.

# Newton-Raphson. Each step is computed FROM the previous estimate.
x     <- 1
trace <- numeric(4)

for (i in seq_len(4)) {
  x        <- x - (x^2 - 2) / (2 * x)
  trace[i] <- x
}

round(trace, 8)
[1] 1.500000 1.416667 1.414216 1.414214

There is nothing to hand to lapply(). The input to iteration 3 does not exist until iteration 2 has run. MCMC, EM, gradient descent, and every iterative optimiser have this shape.

Accumulating results without growing

The pattern for “one row of results per iteration”:

res <- vector("list", length(outcomes))     # pre-allocated LIST
names(res) <- outcomes

for (v in outcomes) {
  res[[v]] <- data.frame(
    outcome = v,
    mean    = round(mean(trial[[v]]), 1),
    sd      = round(sd(trial[[v]]), 1)
  )
}

do.call(rbind, res)                          # combine ONCE, at the end
       outcome  mean   sd
sbp_0    sbp_0 149.5 11.9
sbp_6    sbp_6 144.0 15.1
sbp_12  sbp_12 141.6 15.1

Summary

  • Vectorize when the vector expression states the operation directly.
  • Use a loop when the algorithm has state or the steps need to remain explicit.
  • Preallocate output; repeated growth is the expensive pattern.
  • Prefer functionals with a stable output contract for repeated independent work.
  • Verify equivalence before benchmarking or optimizing.
